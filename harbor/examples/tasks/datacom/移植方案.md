## 0. 一句话结论

`.cac` **本身就是一个评测框架**，Harbor 也是。所以这不是"把 `.cac` 塞进一个 task"，
而是**逐层替换**：

| `.cac` 层 | 换成 Harbor 的什么 |
| --- | --- |
| 步骤2（runner 拉起被测 Agent CLI） | **Harbor 的 agent 阶段** —— Harbor 就是那个 runner |
| 步骤3 / 3.5 / 3.6 / 4 / 5 | **Harbor 的 verifier**（separate 容器里的判分链） |
| 步骤1（上下文校验）+ 用例来源二选一 | Harbor 的 task 校验 + `artifacts` 声明 |
| 阶段3.5 / 4.1（聚合） | **Job 的 `metrics` + `JobStats`** |
| 阶段4.2（HTML 报告） | **移出 verifier**，放宿主侧后处理 |
| comparison / unified_fusion / model_upgrade 场景 | **Job 级**，不是 task 级 |
| bootstrap / driver / plan.json / PlanStore / EPIPE / 整树杀 | **Harbor 已经有了，不移植** |

**最省事的路径**：打分体系（第 7 章）不要手写，用 Harbor 自带的
**rewardkit** 重新表达 —— 它和 `.cac` 的评分模型几乎是同构的（见 §5）。

## 1. 先分清三个层次

`评测工作流.md` 把三件事混在一起讲了，移植时必须拆开：

| 层次 | `.cac` 里的内容 | 移植去向 |
| --- | --- | --- |
| **Task 维度**（评什么） | 用例/子用例、输入、工作目录、参考答案目录、rubric/contract/task.json、打分公式 | **task 目录**（`instruction.md` / `environment/` / `steps/*/tests/`） |
| **Run 维度**（谁来跑） | 技术底座 `cc+datacom-sdd-nce`、模型、agent CLI | **job config 的 `agents:`** ← 不写进 `task.toml` |
| **编排维度**（怎么调度） | bootstrap/driver、plan.json、execution_plan、并行波次、断点 | **Harbor 的 Job/Trial**（大部分直接消失） |

> Harbor 的设计原则明确要求 *separation of concern between agents, tasks, and jobs*。
> 所以 Excel 里"技术底座/模型/agent"这三列**不要**进 `task.toml`，它们是 run 维度。

## 3. 直接消失的三类复杂度（白赚）

### 3.1 目录边界（原文 §3.2 / §3.3）

`.cac` 花了整章处理「评测工作区 vs 被测工作区」：driver 必须留在评测工作区、
`exec_dir` 必须取 `work_dir` 拷贝副本、禁用 `original_work_dir`、相对路径错位、
并行波内多个 subset 无法共存……

Harbor 里：**评测逻辑跑在另一个容器里**（separate verifier），
被测 agent 只能改自己容器的 `/app`，宿主上的 `steps/<name>/artifacts/` 是只读快照。
物理隔离比"同机不同目录"更强，上面那一整章约束**全部消失**。

#### 3.2 编排引擎工程约束（原文 §3.7 / §3.10 的 13 条陷阱）

| `.cac` 约束 | Harbor 的对应机制 |
| --- | --- |
| plan.json 只能由 driver 单写者写（PlanStore 锁内 RMW + 原子写） | `result.json` / `lock.json` 由 Trial 独占写；Job 有 `_trial_completion_lock` |
| stdout 读取必须走独立线程 + `on_tick`（否则超时检查失效） | 容器 exec 由环境实现负责，不由 task 作者碰 |
| 新增子进程一律经 `popen_tree_safe` / `terminate_tree` | 环境 `stop(delete=True)` 整容器销毁 |
| 所有透传 print 走 `safe_print` 防 EPIPE | 容器生命周期与宿主日志解耦 |
| checkpoint `action="check"` 必须并入复核 | Job 的恢复对账重跑未完成的 trial |
| step5 必过清单不得含自身（自指防护） | 不存在这种结构 |
| 未知 Profile 名显式报错 | `task.toml` 由 Pydantic 严格校验，未知字段直接报错 |

**结论：这 13 条陷阱里，只有极少数（比如步骤3 空结果要记 failed）还需要在
`verify.py` 里重新表达，其余全都不移植。**

### 3.3 Excel / 会话 JSON / 会话隔离

`.cac` 的"用例来源二选一"（Excel 副本 or 会话隔离 JSON，二者不得同时存在也不得同时缺失）、
会话 ID 生成与路径对齐、`{session_id}` 目录隔离——这些是为了让 backend 并发下发不互相覆盖。
Harbor 里 task 目录就是唯一来源，trial 目录天然隔离，**整块消失**。

## 4. 必须改造的四个点

### 4.1 被测 Agent CLI → Harbor agent

`.cac` 步骤2 是"runner 拉起被测 Agent CLI"，Harbor 的核心能力就是这件事。
`技术底座 = cc+datacom-sdd-nce` 要拆成：

| tech_stack 片段 | Harbor 表达 |
| --- | --- |
| `cc` | `agents[].name = "claude-code"` |
| `datacom-sdd`（方法论 skill） | `agents[].skills = ["<skill 路径或 org/name>"]` + `[environment].skills_dir` |
| `nce`（其他组件） | `agents[].kwargs` 或 `agents[].env` |
| 模型列 | `agents[].model_name` |

**注意**：
- agent 必须声明 `capabilities.skills = True`，否则 Harbor 会直接拒绝配置
- `结束标识 end_marker` 丢弃 —— Harbor 用 agent 自然结束 + timeout
- 如果被测 agent 不是现成的 CLI（比如是一个内部 HTTP 服务），要包一个
  `BaseInstalledAgent` 子类或 `BaseAgent` 子类，通过 `import_path` 引用

### 4.2 代码变更怎么从 agent 容器进 verifier 容器

**这是移植里最实的一个问题**：separate verifier 看不到 agent 的文件系统。

两条路：

**A. 直接把工作区当 artifact**（简单，可能很大）

```toml
[[steps]]
name = "implement"
artifacts = ["/app"]
```

- 采集是 best-effort，`/app` 会 tar 回宿主再 tar 进 verifier，落在 `/app`
- 缺点：构建产物、`node_modules`、`.git` 一起搬；且与已有的
  `/app/spec.md` 等条目**路径重叠**（Harbor 只告警不报错，会保留第一个）

**B. 用 `[[verifier.collect]]` 钩子打 patch**（轻，推荐）

`collect` 钩子在 **agent 阶段结束后、artifacts 采集之前**，在 **agent 容器**里执行：

```toml
[[steps.verifier.collect]]
command = "cd /app && git add -A && git diff --cached > /logs/artifacts/changes.patch"
service = "main"
timeout_sec = 120
```

- `/logs/artifacts/` 是 Harbor 的**隐式发布目录**，会被自动采集并投递到 verifier 的
  `/logs/artifacts/`，不用再单独声明
- verifier 里：把源工程（烤在镜像里或从只读基线复制）+ `git apply changes.patch`
- 前提：`/app` 里有 git 仓库。没有的话改成 `tar` 快照或 `diff -ru` 对基线
- 声明在 `implement` step 上 → 只在该步执行（`_collect_hooks_for(step)` 只取任务级 + 本步）

> 也可以两者混用：patch 给"代码质量/构建测试"用，`/logs/agent/trajectory.json` 给"过程评判"用。

### 4.3 rubric / contract / task.json 的放置（有泄漏风险）

这些是**判分规则**，绝不能进 agent 容器。放置原则：

```
steps/implement/tests/                 # ← separate verifier 的镜像构建上下文
├── Dockerfile                         # COPY . /tests/
├── test.sh                            # exec python3 /tests/verify.py（或 rewardkit）
├── ground-truth/
│   ├── rubric.md                      # 原 评测用例&答案/tasks/{用例}/{子用例}/ground-truth/
│   ├── contract.md
│   └── reference/                     # 原「参考答案目录」（替代 MR/CodeHub）
└── task.json                          # 原 task.json（compileCommands / focusedTests）
```

**为什么必须放 separate verifier 的镜像里，而不是 shared 步骤的 `tests/`：**

shared 模式的 verifier 会把 `steps/<name>/tests/` 上传到 **agent 容器**的 `/tests`
（`Verifier._resolve_tests()` → `environment.upload_dir(..., "/tests")`）。
Harbor 会在下一步 agent 开始前清空 `/tests`，所以**不会**被后续步骤的 agent 看到；
但规则文件仍然会瞬时存在于 agent 容器里。既然评测有效性依赖 rubric 保密，
就只放在 separate verifier 的镜像里，一步到位。

**奖励机制**：因为 verifier 镜像是 `steps/implement/tests/Dockerfile`（镜像优先级第 2 档），
Harbor **运行期不再上传 `tests/`**（`bundled_tests = True`），`/tests` 的内容完全来自
镜像的 `COPY . /tests/`。改 rubric 只需要重建镜像。

### 4.4 code_similarity 去掉 CodeHub 依赖

`.cac` 的 B1a 代码相似度依赖 CodeHub MR + PAT/account 凭证 + `auto_code_rating` 引擎。
在封闭环境里这块要换掉：

| 原实现 | 替换 |
| --- | --- |
| 从 CodeHub 拉标准答案 MR | 参考答案目录直接烤进 verifier 镜像 `ground-truth/reference/` |
| `auto_code_rating` 引擎逐文件评分 | rewardkit 的 `rk.diff_ratio(path, expected)`，或自定义 `@criterion` |
| `codehub-manifest-diff` skill | 不需要（diff 由 `collect` 钩子的 patch 提供） |
| PAT / account 凭证通道 | 不需要 |

顺带解决两件事：**凭证不用进 verifier 环境**，**MR URL 门控逻辑（步骤3.5 的触发条件）
可以简化成"参考答案目录是否存在"**。

## 5. 打分体系：优先用 rewardkit，不要手写

**这是本次分析里最有价值的结论。** Harbor 自带 `harbor-rewardkit`，
它和 `.cac` 第 7 章的评分模型几乎同构：

| `.cac` 打分元素 | rewardkit 表达 |
| --- | --- |
| 三维度权重 0.50 / 0.40 / 0.10 | `tests/{feature_completeness,code_quality,performance_trace}/` + 根 `reward.toml` 的 `aggregation = "weighted-mean"` + `weights = {...}` |
| 通过条件：`score >= 0.70 AND fc >= 0.60` | 根 `reward.toml` 用 `aggregation = "threshold"` `threshold = 0.7`；或把 fc 做成 `required-pass` 子维度 |
| feature_completeness 逐项 × 得分系数（1.0/0.5/0.0） | 自定义 `@criterion` 逐项算（`unknown` 不进分母），或 `[[criterion]] type = "rubric"` + `levels` |
| `llm_code_analysis` 10 检查项**扣分制** | `[[criterion]] negate = true` + `weight` + `[scoring] aggregation = "weighted-sum"`（唯一支持负权重的模式）★ 几乎是为它设计的 |
| B2 build_pass_rate | `rk.command_succeeds(cmd, cwd=...)` 或自定义 criterion 解析 `build_result.json` |
| B3 test_pass_rate | 自定义 `@criterion` 返回 `passed/total` |
| C1 execution_trace（轨迹/异常/工具错误率） | `[judge] atif-trajectory = "/logs/agent/trajectory.json"` ★ 直接对应<br>+ `rk.trajectory_turn_count(max_turns=N)`、`rk.trajectory_tool_used(...)` |
| C2 response_quality（API 错误/限流/P95） | 自定义 `@criterion` 解析 ATIF 的 `metrics.extra` |
| Position Swap 偏差缓解 | `[judge] samples = N` + 取中位数 + `agreement`（近似，非等价） |
| Confidence Calibration | **无直接对应** → 自定义 criterion 把 confidence 写进 `reward-details.json` |
| `guard`（防 prompt injection） | `[judge] guard = "penalize"` ★ `.cac` 没有，白捡 |
| judge 超时记 0.0 + 错误留档 | 同行为 |
| `{case_id}_integrated_evaluation_result.json` | `reward-details.json` + `harbor view` 的 Verifier Logs → Rewards |
| code-rating 的 `index.html` / `detail/*.html` | reward-details + `harbor view` 渲染 |
| 每用例一份报告 × N | Harbor 每 trial 一份 reward；跨 trial 汇总交给 Job |

**动态加权的例外**：`.cac` 的 `code_quality` 三子维度是**缺失项忽略、剩余按比例重归一化**。
rewardkit 没有这个语义（`optional` 只影响 `required-pass` 门控，不做重归一化）。
→ **建议在 Python 里算好这个重归一化，报一个单一的 `code_quality` 分数**，
不要用三层 reward.toml 硬凑。

**典型骨架**：

```bash
steps/implement/tests/
├── test.sh                          # uvx --from 'harbor-rewardkit==0.2.*' rewardkit /tests
├── reward.toml                      # 顶层聚合：weights + threshold
├── correctness/                     # → feature_completeness
│   ├── rubric.py                    # 逐项判定（读 /tests/ground-truth/rubric.md）
│   └── reward.toml
├── quality/
│   ├── build.py                     # rk.command_succeeds(...)
│   ├── tests_pass.py                # passed/total
│   ├── code_review.toml             # LLM judge：10 检查项 negate
│   └── reward.toml                  # weighted-sum（支持负权重）
└── process/
    └── trajectory.toml              # atif-trajectory + samples
```

```toml
# steps/implement/tests/reward.toml
[[reward]]
name = "reward"
aggregation = "weighted-mean"
weights = { correctness = 5.0, quality = 4.0, process = 1.0 }
```

**两个前置条件**：
1. verifier 镜像里要有 `uv`/`uvx` 和 `harbor-rewardkit`（离线环境就 `pip install` 打进去）
2. rewardkit 的 `workspace` 默认是 `/app` → **被测产物必须投递到 `/app` 下**
   （见 §4.2；`artifacts` 投递时回到原始 source 路径，正好满足）
3. `[steps.verifier.env]` 注入 judge 的 API key（骨架里已注释好位置）

## 6. 必须放弃或降级的四件事

### 6.1 细粒度断点续执行（原文第 10 章）

`.cac` 的步骤级断点（`pending → running → completed/skipped/failed` + `resume_ready` +
"check action 不得丢弃"）依赖 plan.json 持续存在。

Harbor 里：
- **verifier 每次都是新容器**：`/logs/verifier` 在 verify 开始前被 `empty_dirs()` 清空，
  重跑时 trial 目录会被 `rmtree`（重试）或新建（新 job）
- 能保留的断点只有两级：
  - **trial 级**：Job 的 resume 对账（`config.json` 相等则跳过已完成的 trial）
  - **会话级**：`agent.resume_trajectory = true`，多步之间续接原生 session

→ **verifier 内部（3/3.5/3.6/4 之间）的断点放弃**。要么一次跑完，要么整步重跑。
这对判分链的可接受度取决于耗时：如果 build+test 只要几分钟，无所谓；
如果卡在 LLM judge 上几十分钟，靠 `[steps.verifier].timeout_sec` 兜。

### 6.2 产出感知等待（原文 §6.2）

`.cac` 用 `output_aware_wait.py` 监控 `work_dir` 的文件变动，连续 50min 无变动才判超时。
Harbor 只有 `[steps.agent].timeout_sec` 的固定超时。

→ 建议先用固定超时 + 合理余量。真要保留产出感知，得在 agent 阶段外挂一个监控
（Harbor 的 `stream` 模式 + `sync_trajectory` 是类似思路，但那是给轨迹用的，不是给
"任务完成判定"用的）。**成本高，建议降级。**

### 6.3 improving-evaluation 链路B（原文 §9.2）

6 步串行工作流 + 并发子代理 + 经验知识卡片 + HTML 管理报告，**1-3 小时/轮**，
多用例串行可能超过 5 小时。

→ 在 Harbor 里它跑在 verifier 容器内，会直接撞上 `[steps.verifier].timeout_sec`。
建议二选一：

- **降级**：改成基于 ATIF 的轻量异常检测（工具错误率、重复命令、返工次数、
  `trajectory_turn_count`），用 rewardkit 的 trajectory criteria + 少量自定义 criterion
- **移出 reward 链路**：作为宿主侧离线分析（不进分数），产物从 `/logs/verifier`
  回传给宿主脚本

### 6.4 HTML 报告体系（原文第 11 章）

`.cac` 有 8 种报告模板 + collect→LLM 填字段→render→封面页的链路 + JSON Schema 校验。

**建议整体移出 verifier**，理由：

1. verifier 的职责是产出 reward；HTML 是给人看的
2. 报告要 LLM 填 `[LLM]` 字段 → 额外 LLM 调用 + 不确定性**会污染判分链路**
3. Harbor 有自己的 viewer（能渲染 ATIF、能展示 `reward-details.json`）
4. `verify_final_deliverables` 那套"封面页缺失触发整体重试"的逻辑在 Harbor 里没必要

若确实要保留：让 verifier 把 `report_data.json` 回传到 `/logs/verifier/report-data.json`，
宿主上一个独立脚本（**不属于 task、不属于 verifier**）渲染 HTML。

> 回传方式：verifier 容器里写 `/logs/verifier/**` 的任何文件都会回到宿主
> `<trial_dir>/steps/implement/verifier/`（docker 下是实时 bind mount）。

## 7. 场景体系的重新落点

`.cac` 的 4 个场景本质上是**两种粒度**混在一个 session 里：

| `.cac` 场景 | 粒度 | Harbor 落点 |
| --- | --- | --- |
| `answer_comparison`（单用例） | trial | **task 的 verifier**（rewardkit） |
| `performance_comparison` | 2 个 trial | 两个 trial 各出一份 `performance_trace` → **Job 的 metric** 或宿主对比脚本 |
| `unified_fusion`（聚合） | 整个 job | **Job 的 `metrics`**（按 dataset 分组）+ `JobStats.evals` |
| `model_upgrade` | 2 个 job / 2 个 agent | **`agents:` 里放两个模型跑同一 dataset** ★ |

★ **model_upgrade 是白捡的**：Harbor 的 `agents: [...] × datasets: [...]` 笛卡尔积会直接
产生对比矩阵，`JobStats.evals` 的 key 是 `agent__model__dataset`，
天然就是 `.cac` 想要的"能力对比矩阵"：

```yaml
# job config
datasets:
  - path: <datacom 用例集目录>
agents:
  - name: claude-code
    model_name: <旧模型>
  - name: claude-code
    model_name: <新模型>
n_concurrent_trials: 4
```

对比报告的触发条件（`.cac` 是"≥2 个不同 tech_stack"）在 Harbor 里就是
"`evals` 里有 ≥2 个 key"。

同理，`(tech_stack, work_dir)` 分组的并行/串行策略：
- 不同组可并行 → `n_concurrent_trials`
- 同组要串行（共享资源）→ `agents[].concurrency_group` + `agents[].n_concurrent = 1`

## 8. Excel → dataset + job config

Excel 一行同时含 task 维度和 run 维度，**adapter 要把它拆开**。

参照 `adapters/swebench/` 的结构（`adapter.py` / `run_adapter.py` / `task-template/`）
和 `harbor task migrate` + `TerminalBenchMapper` 的模式，写一个
`adapters/datacom_eval/`：

| Excel 列 | 去向 |
| --- | --- |
| 用例 / 子用例 | task 目录名 + `[task].name` |
| 输入 | `steps/*/instruction.md` 的内容来源 |

## 9. 目标目录结构

```bash
examples/tasks/datacom/                     # 1 个 task = 1 个（用例, 子用例）
├── task.toml
├── environment/                            # = 被测工作区的初始状态（替代 work_dir 拷贝）
│   ├── Dockerfile
│   └── seed/                               # 源工程种子（可选）
└── steps/
    ├── new_spec/                           # ┐
    │   ├── instruction.md                  # │  SDD 三阶段
    │   ├── tests/test.sh                   # │  （中间步 verify 置空）
    │   └── solution/solve.sh               # ┘
    ├── new_plan/  ...
    └── implement/
        ├── instruction.md
        ├── solution/solve.sh
        └── tests/                          # ★ 移植后的 .cac 判分链，全在 verifier 镜像里
            ├── Dockerfile                  # 装 uv/rewardkit（+ 可选 judge 用 CLI）
            ├── test.sh                     # 入口
            ├── reward.toml                 # 顶层权重 / 通过阈值
            ├── correctness/                # ← feature_completeness
            ├── quality/                    # ← code_quality（build / test / code review）
            ├── process/                    # ← performance_trace
            ├── ground-truth/               # ← 原 评测用例&答案/.../ground-truth/
            │   ├── rubric.md
            │   ├── contract.md
            │   └── reference/
            └── task.json                   # ← 原 task.json（compileCommands/focusedTests）
```

`task.toml` 关键片段：

```toml
multi_step_reward_strategy = "final"

[[steps]]
name = "implement"

# 送进 verifier 容器的东西（回到原始 source 路径）
artifacts = [
    "/app/spec.md",
    "/app/plan.md",
    "/logs/agent/trajectory.json",
]

# 在 agent 容器里、采集之前把代码变更快照成 patch
[[steps.verifier.collect]]
command = "cd /app && git add -A && git diff --cached > /logs/artifacts/changes.patch"
service = "main"

[steps.verifier]
timeout_sec = 3600.0
environment_mode = "separate"

[steps.verifier.environment]
network_mode = "public"        # LLM judge 需要出网
cpus = 2
memory_mb = 4096

# judge 的 API key 从宿主注入
[steps.verifier.env]
ANTHROPIC_API_KEY = "${ANTHROPIC_API_KEY}"
```

## 10. 落地路线（建议分 6 步）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **P1** | 用现有骨架跑通链路：agent → artifacts → collect 钩子 → separate verifier | `harbor run -a oracle` 能跑完，产物在 `steps/implement/verifier/` |
| **P2** | 判分最小闭环：`task.json` 的 compileCommands/focusedTests → programmatic criteria | reward 只出 `build` / `test` 两个维度 |
| **P3** | `rubric.md` → rewardkit judge criteria，先只上 `feature_completeness` 一维 | 分数与 `.cac` 对同一份产物的人工判分对齐 |
| **P4** | 补齐三维度 + `reward.toml` 的 weights/threshold，表达 0.5/0.4/0.1 与通过条件 | `reward` 与 `.cac` 的最终分一致（±可接受偏差） |
| **P5** | 过程维度（`atif-trajectory` + turn/tool criteria）+ Job 级对比（两个模型跑同一 dataset） | `evals` 出现 ≥2 个 key，对比数据可读 |
| **P6**（可选） | 宿主侧 HTML 报告（消费 `/logs/verifier/report-data.json`） | 报告与 `.cac` 的交付物清单对齐 |

> P2/P3 之间可以先不做 LLM 判分，用 programmatic criteria 跑通闭环，成本最低。
