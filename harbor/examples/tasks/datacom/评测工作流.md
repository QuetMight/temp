## 1. 系统架构总览

`.cac/` 下的评测系统采用 **确定性 driver 编排 + Skill 技能 + 脚本工具** 的三层架构（编排已全面脚本化，LLM 仅保留评估/报告 3 个一次性节点）：

```
用户调用 / backend 下发
  │
  ├─→ rubric-extractor (独立Agent，前置阶段)
  │     └─→ 生成 contract.md + rubric.md (评测规则集)
  │
  ├─→ run_session_bootstrap.py (会话入口：初始化 + 拉起 driver)
  │     │
  │     └─→ run_session_driver.py (确定性编排，纯 Python 状态机)
  │           ├─→ 步骤1: 准备上下文（用例来源二选一校验）
  │           ├─→ 步骤2: 执行测试 + 产出感知等待（output_aware_wait.py）
  │           ├─→ 步骤3: 采集执行过程（collect_subset.py）
  │           │     ├─→ collector 链路A: 分析报告 + summary JSON
  │           │     └─→ improving-evaluation skill（链路B 日志深度分析）
  │           ├─→ 步骤3.5: 代码质量评分（prepare_code_rating.py → code-rating skill）
  │           ├─→ 步骤3.6: 构建与测试执行（run_build_test.py）
  │           ├─→ 步骤4: evaluation-agent (codeagent CLI 一次性调用，可并行)
  │           │     └─→ evaluation-scenario skill
  │           │           ├─→ answer_comparison (答案对比)
  │           │           ├─→ performance_comparison (性能对比)
  │           │           ├─→ unified_fusion (统一融合)
  │           │           └─→ model_upgrade (模型升级)
  │           │                 └─→ integrated-evaluation skill (统一多维度评估)
  │           ├─→ 步骤5: 验证完整性
  │           ├─→ 阶段3.5: 会话级聚合评估（仅 unified_evaluation=true）
  │           └─→ 阶段4.2: report-generator (codeagent CLI 一次性调用)
  │                 ├─→ collect_report_data.py  (数据收集)
  │                 ├─→ render_report.py        (HTML渲染)
  │                 └─→ generate_report_index.py (封面页 index.html，必交)
```

### 核心设计原则

1. **两阶段架构**：阶段A（会话初始化 + 上下文校验，初始化由 run_session_bootstrap.py 前置完成）→ 阶段B（计划执行）
2. **异常不中断**：即使被测任务失败，仍需执行采集和评估步骤
3. **断点续执行**：执行计划文件是断点续执行的唯一状态源
4. **脚本主导**：编排、确定性数据采集和HTML渲染通过Python脚本完成，LLM只负责评估判断和字段填充
5. **数据完整性**：第0步强制检查采集数据完整性，缺失如实标注、绝不编造
6. **规则集前置**：rubric-extractor 在评测前预先生成 `rubric.md`/`contract.md`，作为 `feature_completeness` 维度的核心数据源

## 2. 编排体系（driver + LLM 节点）

### 2.1 run_session_driver（确定性编排）

**职责**：评测端到端流程的总调度器（纯 Python 状态机，`.cac/scripts/run_session_driver.py`）

| 能力 | 说明 |
|------|------|
| 会话上下文校验 | 校验调用方传入的 session_id 与执行计划契约（初始化由 run_session_bootstrap.py 在启动前完成） |
| 断点检测 | 经 evaluate_checkpoint.py 扫描计划文件、解析断点 |
| 并行调度 | 按 plan 的 execution_plan 并行调度（parallel 组内线程池，PlanStore 锁保并发写安全） |
| 测试执行管理 | 子进程启动 run_excel_tests.py + output_aware_wait.py 产出感知等待，超时整树杀 |
| 评估调用编排 | 每个 subset 经 codeagent CLI 一次性调用 evaluation-agent（并行波内随线程并发）；统一融合场景额外一次聚合调用 |
| 结果汇总 | 统计通过率、平均分；调用 aggregate_evaluator_results.py 汇总 |
| 报告生成委托 | 经 codeagent CLI 调用 report-generator 生成 HTML 报告 |

**硬性约束**：
- LLM 仅保留 3 个一次性 CLI 节点（evaluation-agent ×2、report-generator），编排本身零 LLM 参与
- 禁止在 driver 内新增长阻塞读（stdout 读取单点收敛于 `_stream_subprocess`）
- 禁止 driver 自行执行评估任务（评分必须委托给 evaluation-agent）
- 步骤2 终止三道防线：产出感知监控超时（50min）/ stdout 静默兜底（150min）/ 全局 24h 上限，超时即整树杀（常量见 §3.7）

### 2.2 evaluation-agent（评估SubAgent）

**职责**：一次性评估专家，接收 driver 调用（codeagent CLI）→ evaluation_prepare.py 脚本化取参 → 判断模式 → 调用 evaluation-scenario skill → evaluation_finalize.py 脚本化组装返回值

**两种调用模式**：

| 模式 | 触发条件 | 评估范围 | 核心产出 |
|------|---------|---------|---------|
| 模式一：单子用例集评估 | 每个 subset 执行完步骤1-3.6 后 | 单个 subset 逐用例 | `{case_id}_evaluation.json` + `{case_id}_integrated_evaluation_result.json` + HTML 报告 |
| 模式二：会话级聚合评估 | 所有 subset 阶段一完成后 | 全会话所有 subset | 融合报告 + 评测记录 |

**执行步骤**（取参与后处理均脚本化，禁止手工解析 plan.json / 拼装返回值）：
1. 调用 `evaluation_prepare.py` 提取上下文：plan 加载与 subset 定位 → 路径数据提取 → 第0步数据完整性检查（缺失记 data_gaps）→ skill args 组装（stdout JSON 契约）
2. 调用 evaluation-scenario skill（按脚本输出 args 透传）
3. 调用 `evaluation_finalize.py` 组装返回值：算术矫正 → 字段回填 → 产物磁盘验证（谎报路径强制置空）→ return_text（stdout JSON 契约）；模式二聚合评估不经此步，由 skill 直接产出

### 2.3 report-generator（报告SubAgent）

**职责**：生成最终交付的 HTML 报告

**执行流程**：数据收集（collect_report_data.py）→ LLM字段填充 → HTML渲染（render_report.py）→ 封面页生成（generate_report_index.py）→ 产物验证

**支持报告类型**：
- `single:{subset_id}` — 单子用例报告（每个 subset 一份，含主报告 + 产物评估子报告 + 过程评估子报告，共 3 个 HTML）
- `comparison:left=...,right=...` — 对比报告（对比场景必交，含主报告 + 产物评估子报告 + 过程评估子报告，共 3 个 HTML）
- 封面页 `reports/index.html` — 报告总览 + 跳转入口，**所有场景必交**（独立链路：直接读 plan.json + evaluator_results.json，不走 collect → schema → render 主链路）

### 2.4 rubric-extractor（规则提取Agent）

**职责**：分析软件工程实例文件包、需求、源码、测试和参考补丁，提取实现无关的隐藏行为契约与百分制盲评标准

**产出**：
- `contract.md` — 隐藏行为契约（实现无关）
- `rubric.md` — 盲评产品评分标准（总分严格100分）

**核心原则**：评价候选实现是否满足产品需求，而不是评价候选实现是否复现参考答案。参考答案的证据优先级最低。

**与评测流程的关系**：rubric-extractor 产出的 `rubric.md` 和 `contract.md` 被放置在 `评测用例&答案/tasks/{用例名}/{子用例名}/ground-truth/` 下，作为 integrated-evaluation 的 `feature_completeness` 维度核心数据源（rubric.md）和辅助参考（contract.md）。这是评分标准重构的关键配套——`feature_completeness` 维度从 rubric.md 解析功能项清单逐项打分，依赖 rubric-extractor 预先生成规则集。

**证据优先级**（从高到低）：

| 优先级 | 证据来源 |
|--------|----------|
| 1 | 任务需求中的明确要求 |
| 2 | Issue、用户故事和验收条件 |
| 3 | 原始仓库已有的公共接口与兼容性约束 |
| 4 | 原始仓库中的真实调用链和数据流 |
| 5 | 原始仓库已有测试所体现的稳定行为 |
| 6 | 项目明确采用的协议、数据格式或行业标准 |
| 7 | 构建系统、CI 和运行环境约束 |
| 8 | 参考答案、Gold Patch 或参考 Diff（优先级最低） |

## 3. 流程组织详解（bootstrap / driver / 目录边界）

> 本章是第 1、2 章架构总览的展开：入口引导层与编排引擎层的职责边界、执行目录的物理边界、
> steps_progress 各步骤的执行位置、pipeline Profile 体系、并行调度细节与引擎工程约束。
> 对应实现：`run_session_bootstrap.py`（190 行）、`run_session_driver.py`（2220 行）、
> `pipeline/base.py` / `pipeline/registry.py` / `pipeline/steps/builtin.py`。

### 3.1 职责划分总表：bootstrap vs driver

**bootstrap = 引导层**：确保会话有合法 plan，然后把控制权完整交给 driver，本身不做任何编排。
**driver = 编排引擎**：评测编排的唯一实现路径，全系统唯一的 plan.json 写者进程。

| 维度 | `run_session_bootstrap.py` | `run_session_driver.py` |
|------|---------------------------|------------------------|
| **角色** | 引导层 / 入口适配器 | 编排引擎 / 状态机 |
| **生命周期** | 初始化完成 + 拉起 driver 后只等退出码 | 全程持有：校验→断点检测→调度→执行→聚合→报告 |
| **对 plan.json** | 只探测存在性（**不读内容、不写**） | 唯一写者（PlanStore 锁内 RMW + 原子写）；只读消费 + 全量状态落盘 |
| **初始化** | ✅ 调 `prepare_eval_session`（幂等，plan 已存在跳过） | ❌ 只做断点检测（plan 缺失 → 退出码 2 并提示先跑 bootstrap） |
| **断点语义** | 粗粒度：plan 存在即跳过初始化，`--resume` 仅透传 | 细粒度：`evaluate_checkpoint` 按 step 状态决定跳过/重跑/复核 |
| **步骤执行** | ❌ 无感知 | ✅ 全部 7 步 + 会话级阶段 |
| **并行调度** | ❌ | ✅ execution_plan 波次调度 + 线程池 |
| **LLM 调用** | ❌ | ✅ 3 个 codeagent CLI 节点（评估/聚合/报告） |
| **输出契约** | 纯透传（backend 流式采集依赖） | 心跳日志 + JSON 契约行（`safe_print` + EPIPE 降级） |
| **退出码** | 透传 driver 的退出码；初始化失败 = 1 | 0=全成；1=有失败 subset 或报告未过；2=plan/契约/Profile 错误 |
| **可测试性** | 无独立测试（逻辑太薄） | `test/test_run_session_driver.py`、`test_pipeline_registry.py` 等 |

**单向依赖**：bootstrap → driver，driver 从不回调 bootstrap；两者通过 plan.json 文件系统契约解耦
（路径规则 `评测执行历史-cac/execution_plans/{session_id}_plan.json` 双侧对齐）。

**fail-fast 边界**：初始化失败死在 bootstrap（不启动 driver）；plan 结构损坏 / Profile 错误死在
driver 阶段A/C（退出码 2）；步骤失败不中断（"异常不中断"语义，步骤3/4 强制执行）。

**bootstrap 存在的意义**：backend 下发命令需要一个**稳定的执行入口**（幂等初始化 + 心跳透传 +
退出码契约），而 driver 需要保证"拿到合法 plan 才启动"——两者合并后，backend 只需记住一条命令
`run_session_bootstrap.py --session-id X`。

#### bootstrap 三项职责

1. **会话 ID 与输入解析**（`main`）：`--session-id` 缺省时生成 `YYYYMMDD_HHMMSS_{8位hex}`
   （与 backend `_build_eval_session_id` 的 cac 格式对齐，保证 plan 路径可对齐）；
   **会话隔离 JSON 探测**——`--excel` 走默认值且 `评测用例&答案/{session_id}/agent评测用例.json`
   存在时优先使用（backend cac 模式多任务并发下发互不覆盖共享 Excel 的关键）。
2. **幂等初始化**（`run_init`）：plan 文件已存在 → 跳过初始化（重续场景）；不存在 → 调
   `initiator/prepare_eval_session.py` 的 `prepare()`（验证用例集 → 拆分子用例集 → 生成执行计划
   → 产物骨架）；**双重校验**——脚本返回 success 后还要确认 plan 文件真实落盘，防止
   "返回成功但未生成"；任一环节失败 → 非零退出（1），**不启动 driver**。
3. **拉起 driver**（`run_driver`）：`subprocess.Popen` 启动 `run_session_driver.py`，透传
   `--session-id / --workspace / --resume / --profile`；**stdout/stderr 原样透传、退出码原样返回**
   （backend 流式采集/心跳依赖此行为）；仅处理 `KeyboardInterrupt` → terminate 返回 130。

#### bootstrap 明确不做的事

- ❌ 不读 plan 内容、不做契约校验（driver 的 `validate_plan_contract` 负责）
- ❌ 不做断点检测（`evaluate_checkpoint` 负责）
- ❌ 不执行任何步骤、不做调度、不写 plan
- ❌ 不感知步骤语义（步骤1-5 对它是黑盒）

### 3.2 目录边界：评测工作区 vs 被测工作区

**driver 执行在评测工作区（workspace）根目录，不在被测工作区中。** 被测项目的工作目录（work_dir）
是初始化阶段为每个子用例集准备的拷贝副本，driver 从不进入其中执行——只有被测 Agent（经 runner）
在里面跑。

#### 三层目录关系

```
评测工作区（workspace，driver 的 cwd 与 --workspace）
├── .cac/                              ← driver/runner/监控/采集脚本都在这里
├── 评测用例&答案/{session_id}/        ← backend 下发的会话隔离用例 JSON（cac 模式）
├── 评测执行历史-cac/
│   ├── execution_plans/{session_id}_plan.json   ← driver 状态源（唯一写）
│   ├── logs/driver_{session_id}.log             ← driver 文件日志
│   └── {session_id}/（会话产物根 timestamp_dir）
│       └── {subset_id}/
│           ├── work_dir/                ← ★ 被测项目副本（被测工作区）
│           └── 评测输出/                ← runner/agent 产物落这里
```

#### 各进程的执行位置

| 进程 | cwd | 说明 |
|------|-----|------|
| bootstrap | 评测工作区根（`workspace = Path.cwd()`） | backend SSH 或本地在 workspace 根下发 |
| **driver** | **评测工作区根**（bootstrap `Popen(cmd, cwd=str(workspace))`） | plan、日志、`.cac/` 脚本路径全部按 workspace 根相对解析 |
| runner（run_excel_tests.py） | **被测工作区**（driver 以 `cwd=work_dir` 拉起） | 连同它拉起的被测 Agent CLI 一起在 work_dir 副本里执行 |
| 被测 Agent CLI | 被测工作区（由 runner 带入） | 在 work_dir 副本里改代码、写产物 |
| output_aware_wait 监控 | 评测工作区，但**跨目录观测** work_dir 文件变动 | 与被测 Agent 同一信号源 |

**硬约束**：plan 同时有 `original_work_dir`（源工程）与 `work_dir`（拷贝副本），driver 侧
`exec_dir` 必须取 `work_dir`（拷贝后），**禁用 `original_work_dir`**——保证被测 Agent 的改动
只落在副本里，不污染源工程。

#### 交互模式与设计理由

- driver 与被测工作区**物理隔离**，只做两类操作：
  - **观测**：步骤2 拉起 `output_aware_wait.py` 监控 work_dir 文件变动（产出感知信号）；
  - **收割**：步骤3/3.5/3.6/4 从 `{output_dir}/评测输出/`、work_dir diff 等产物路径采集数据。
- 一个会话含多个子用例集（多个不同被测工作目录，来自不同仓库/技术底座），driver 必须留在
  评测工作区统一编排并写同一份 plan.json——如果钻进某个被测工作区执行，相对路径
  （`评测执行历史-cac/`、`.cac/`）会错位，且并行波内多个 subset 无法共存。
- 远端（agent=cac）场景：整个 `.cac` 部署 + 用例 JSON 下发到 slave 节点的评测工作区，
  bootstrap → driver 都在那台执行机运行；被测工作区是同机上的项目副本（支持 worktree 形态），
  文件监控与产物读取直接走本地路径。
- **契约**：状态和脚本归评测工作区，执行和产物归被测工作区，plan.json 的
  `work_dir` / `output_dir` / `timestamp_dir` 路径字段是两侧之间的路径契约。

### 3.3 steps_progress 七步执行位置：启动 cwd vs 实际作用域

**判断某步跑在哪不能只看步骤名，要区分两个概念：「步骤进程的启动 cwd」（driver 从哪里拉起
脚本）和「步骤的实际作用域」（动的是哪片目录）。**

| 步骤 | 进程启动 cwd | 实际作用域 | 说明 |
|------|------------|-----------|------|
| **step1_prepare** | 无子进程（driver 进程内逻辑） | 评测工作区 | 纯 plan 字段校验：work_dir / excel_copy / usecase_json 存在性检查；用例来源二选一（Excel 副本或会话隔离 JSON，二者不得同时存在）；失败 → subset 置 failed 且**中断**（后续步骤依赖其产物路径校验） |
| **step2_execute** | ★ **被测工作区** `cwd=work_dir` | **唯一整个跑在被测工作区的步骤** | runner 连同被测 Agent CLI 在 work_dir 副本里改代码、写产物；监控进程从评测工作区跨目录观测 work_dir 文件变动；终止判定三值契约：normal_return（exit=0）/ abnormal_kill（exit_code≠0）/ timeout_fallback（监控超时或全局超时，driver 主动树杀）；runner 脚本启动前有存在性检查；plan.json 模式必传 `--output-dir`（collector 按 `{output_dir}/评测输出/` 扫描） |
| **step3_collect** | 评测工作区 | 混合（读被测工作区、写会话产物区） | `collect_subset.py` 在 workspace 跑，读取被测工作区产物；**空结果显式失败**：`cases=[]`（识别 0 用例）或 stdout 无法解析出 collector JSON → 记 `failed` 而非 completed（stdout 解析不以 exit_code==0 为前提）；仍按"异常不中断"返回 True 继续步骤4 |
| **step3_5_code_rating** | 评测工作区 | 混合 | **条件门控**：参考答案目录中提取 MR URL，无 → skipped；三种终态：完成（exit=0）/ **partial**（超时但已有部分产出 → completed + `partial=true`，保留评分产出）/ skipped（失败或超时且无部分产出，skip_reason + stdout 尾部 20 行留档）；不阻断 |
| **step3_6_build_test** | 评测工作区（外层脚本） | ★ **双层结构**：内层在被测工作区 | 外层 `run_build_test.py` 在 workspace 跑（读预制 task.json、对 plan **只读不写**，结果经 stdout JSON 契约回报，driver 解析后经 PlanStore 落盘）；内层解析出的 `compileCommands`/`focusedTests` 每条命令 `cwd=work_dir` 在**被测工作区内执行**（构建/测试命令、gradle daemon 等孙进程，树杀约束同样适用）；产出 `build_result.json`/`test_result.json`，作为 code_quality 维度 build_pass_rate/test_pass_rate 子维度来源 |
| **step4_evaluate** | 评测工作区 | 评测工作区 | `codeagent --agent evaluation-agent` 从 workspace 启动；返回值经宽松解析（key=value，全角逗号兼容），score / evaluation_file 任一缺失即 failed（SKILL 4.3）；从 integrated JSON 读盘提取嵌套契约字段（B1）；评估产物路径写入 subset_artifacts.json；**超时也记 failed 继续步骤5**——异常不中断 |
| **step5_verify** | 无子进程（driver 进程内检查） | 评测工作区 | 检查点：必过清单与条件步骤（3.5/3.6）completed\|skipped 口径均从 Profile 步骤聚合（`Step5Verify.verify()` 恒空 = 自指防护）；通过 → subset 置 completed；不通过 → step5 记 failed + subset 置 checkpoint_failed + 失败现场落盘，需人工介入 |

**结论**：

1. **进程视角**：七步中五步（1/3/3.5/4/5）全部发生在评测工作区；只有 **step2 的 runner**
   整体切到被测工作区。
2. **效果视角**：真正"进入"被测工作区动手的只有两处——**step2**（被测 Agent 在 work_dir
   执行任务，评测主体行为）与 **step3.6 内层**（构建/测试命令在 work_dir 验证 Agent 产出）。
3. **其余步骤都是"遥控"**：step1/5 只碰 plan.json；step3/3.5/4 从被测工作区**只读收割**
   （读产物、读 diff），再写回评测工作区的会话产物目录和 plan。
4. 被测工作区只属于被测 Agent 和验证命令（保证评测环境纯净、可复现）；一切编排状态、脚本、
   采集评估逻辑都留在评测工作区。

### 3.4 driver 主流程五阶段

| 阶段 | 内容 | 关键机制 |
|------|------|---------|
| 阶段A | plan 存在性检查 + **契约校验**（`validate_plan_contract`） | session_id/subset_details 必备键、subset_id 重复拒绝、cac JSON 链路（usecase_json_path 非空）要求 output_dir 非空；失败退出码 2 |
| 阶段B | **断点检测**：子进程调 `evaluate_checkpoint.py` | 得到每个 subset 的 action（execute/check）；`action="check"`（状态悬空）必须并入复核队列，不得静默丢弃（B2） |
| 阶段C | **Profile 解析** | 优先级：plan 顶层 `pipeline` 字段 > CLI `--profile` > 默认；未知 Profile 名显式 ValueError → 退出码 2（不静默回退） |
| 阶段D | **subset 调度执行** | 见 3.6 并行调度 |
| 阶段E | **会话级阶段**（按 `profile.session_stages` 声明遍历） | 3.5 聚合 → 4.1 汇总 → aggregate 脚本 → 4.2 报告；实现函数经 `func_name` 从模块 globals 动态解析（测试打桩兼容） |

**退出码契约**：`0` = 全部完成；`1` = 存在失败 subset，或 subset 全成功但报告生成/交付物验证
未通过（阶段4.2 重试后仍失败也归 1）；`2` = 会话/plan 缺失、契约校验失败、Profile 解析失败。

### 3.5 pipeline Profile 体系（STEP_ORDER 单一事实源）

**STEP_ORDER 单一事实源**：`pipeline/registry.py` 从 `steps/builtin.py` 的 `BUILTIN_STEPS`
清单导出，driver 与 `evaluate_checkpoint` 双侧 import 消费（后者保留独立运行回退定义，
一致性由 `test/test_pipeline_registry.py` 契约测试看护），禁止任何一侧维护第二份顺序清单。

`EvaluationProfile` 三段声明：

| 字段 | 内容 | 默认值（code_gen_v1） |
|------|------|------------------------|
| `steps` | 子用例集步骤清单（含门控/断点跳过条件/检查点贡献） | `BUILTIN_STEPS` 7 个 Step 类：step1_prepare / step2_execute / step3_collect / step3_5_code_rating(optional) / step3_6_build_test(optional) / step4_evaluate / step5_verify |
| `session_stages` | 会话级阶段编排声明 | session_aggregate → update_plan_results_summary → run_aggregate_script → session_report |
| `llm_nodes` | LLM 节点规格声明（agent 名 / 超时） | step4_evaluate→evaluation-agent、session_aggregate→evaluation-agent、session_report→report-generator（timeout=0 = 引擎默认 48h） |

- **四件套接口**（`BaseStep`）：`run` / `should_run` / `verify` / `resume_ready`；
  `optional=True` 的步骤（3.5/3.6）checkpoint 允许 completed|skipped。
- **依赖规则**：base 零内部依赖、registry 不 import driver、steps 延迟 import driver（防循环）。
- **单源收敛**：断点跳过条件单源于各 Step 的 `resume_ready()`（checkpoint 经
  `registry.resume_ready_by_name` 按名委托）；磁盘存在性判定单源于
  `pipeline.base.path_dict_has_existing_file`；条件步骤门控单源于 `should_run()`
  （3.5 MR URL 门控、3.6 task.json 门控）。
- **自指防护**：`verify` 聚合**不含 step5_verify 自身**——它是检查点自身，status 要等检查结束
  才写，列入必过则永远 pending，所有 subset 必然 checkpoint_failed。
- **扩展方式**：新增/删除评测步骤改 `BUILTIN_STEPS` 即可；新增 Profile（如 spec 文档评测）
  注册进 registry；`get_profile` 对未知名称显式报错（ValueError → driver 退出码 2，不静默回退
  ——静默回退会把写错的 Profile 名吞成默认流程，产物与预期不符且无提示）。
- **会话级阶段**：实现函数单点留在 driver（重试、warnings 累积、交付物验证等机制不随评测对象
  变化），经 `func_name` 动态解析；`SessionStage.args` 声明参数名（store/session_id/workspace/
  plan_file/plan/profile），其中 `plan` 为该阶段执行时从 PlanStore 重读的最新状态。
- **LLM 节点超时**：经 `resolve_llm_node(profile, node_name, fallback_agent)` 解析——声明
  timeout>0 以声明为准，0/未声明 = 引擎默认 `AGENT_CALL_TIMEOUT_SECONDS`（48h）。

### 3.6 并行调度详解（阶段D）

- 消费 plan 的 `execution_plan` 数组：`parallel=true` 组内每 subset 提交 ThreadPoolExecutor，
  `parallel=false` 组内顺序执行；组与组之间保持数组顺序。
- `execution_plan` 缺失/为空 → 回退全串行（兼容旧 plan）；execution_plan 未覆盖到的
  pending subset 追加为串行兜底。
- **max_workers 优先级**：CLI `--max-workers` > plan 顶层 `max_workers` > 默认 4。
- 相邻同 parallel 标记的 subset 合并为一"波"（wave）：并行波进线程池，串行波逐个执行。
- **失败隔离**：`_subset_runner` 在线程内捕获所有异常（不向外抛）——单个 subset 执行异常 →
  记日志 + subset 置 failed，继续下一个；线程池 `fut.result()` 处再兜底一层。
- **LLM 节点并发边界**：步骤4 evaluation-agent 属 subset 内步骤，**随线程池并行**（各 subset
  产物目录隔离 + PlanStore 锁互斥保证 plan 写安全）；仅会话级 LLM 节点（阶段3.5 聚合 /
  阶段4.2 报告）在 join 之后主线程**串行**。
- **步骤级状态更新**：线程内只做步骤级 plan 更新（经 PlanStore 锁内 RMW）；每步执行前经
  `_fresh_subset` 从磁盘重读最新状态（并行窗口内其他线程可能已更新），不沿用上游旧 dict。

#### PlanStore：plan.json 唯一写者（A1 单一写者收权）

- 全系统只剩 driver 一个 plan 写者进程（run_build_test.py 已去写化，经 stdout JSON 契约回报，
  driver 解析后经 PlanStore 落盘）。
- 每次变更**锁内 load-改-save 全序列**（`threading.Lock`）+ 原子写（tmp + `os.replace`）。
- 核心方法：`load` / `save` / `find_subset` / `update_subset`（支持 callable 变更函数）/
  `get_step` / `update_step` / `update_plan_field`。
- 会话级操作（results_summary / 聚合 / 报告）保持主线程调用，不在并行窗口内。

### 3.7 引擎工程约束（单点收敛，禁止复制）

| 机制 | 单点位置 | 约束 |
|------|---------|------|
| **stdout 防竞态泵（B4）** | `lib/_proc_runner.py: stream_subprocess` | `proc.poll()≠None` 与 reader 线程 put 最后一行之间存在窗口，退出判定必须先 `reader.join()` 再 drain 残留行；阻塞式 `readline()` 会卡住主循环导致超时检查失效（实测 runner 静默时延可从 7s 恶化到 118s）——stdout 读取必须放独立线程、主循环短间隔轮询 queue；`_run_script` / `_stream_llm_call` / 步骤2 三方共用，**新等待通道一律经 `on_tick` 闭包注入，禁止复制该循环** |
| **整树杀（B3）** | `lib/_proc_runner.py: popen_tree_safe / terminate_tree` | 全部 Popen 经 `popen_tree_safe`（POSIX `start_new_session`）创建，终止走 `terminate_tree`（Windows `taskkill /F /T`、POSIX `killpg`）——runner 与被测 Agent 是父子关系，超时终止若只杀主进程，孙进程孤儿化继续写产物、与步骤3 采集竞态；**新增 .cac 子进程点一律经这两个原语，禁止裸 `subprocess.run`** |
| **EPIPE 降级** | `run_session_driver.py: safe_print / _SafeStdoutHandler / mark_stdout_broken` | 背景（20261008_210143 生产事故）：backend SSH 通道中途断开后，driver 所有 print 抛 BrokenPipeError 冒泡，subset 被误判 failed、过程数据全缺。约束：**stdout 只是 backend 心跳透传通道，编排状态源是 plan.json + 会话文件日志，通道断开属传输层故障，不得改写编排语义**——所有透传 print/JSON 契约行必须走 `safe_print`（禁止裸 `print`）；logging 心跳 handler 自行 write/flush 并拦截 EPIPE（不走 `super().emit()`，其内部 handleError 会向已断 stderr 二次回写）；`mark_stdout_broken` 幂等降级：fd 0/1/2 → devnull（dup2，根治 atexit flush 残余写点）+ 控制台 handler 改写 devnull，日志仅剩 FileHandler 落盘。测试 `test/test_stdout_epipe.py` 看护 |
| **LLM 调用超时语义** | `_stream_llm_call` | 内部经 `_stream_subprocess` 自管超时（kill 进程树 + 返回 `timed_out` 标记），**从不抛 `subprocess.TimeoutExpired`**——调用侧只判 `result["timed_out"]`，不要写 try/except 死分支；`timed_out` 只认进程树终止标记，不得用总耗时重算（进程正常退出但总耗时恰好超过 timeout 时会误报，导致丢弃有效评估/报告结果） |
| **LLM 节点心跳** | `_stream_llm_call` | stdout 逐行透传（LLM 执行期间持续产出，兼作 backend 心跳，避免数小时静默被误判进程死亡）；stderr 单独收集供失败诊断，不混入 stdout 污染 JSON 解析；注入 `OPENCODE_EXPERIMENTAL_BASH_DEFAULT_TIMEOUT_MS=43200000`（本地直跑时兜底） |
| **JSON 契约提取** | `lib/_proc_runner.py: extract_json_objects` | collect / build_test / rating 等脚本的数据回报契约，从 stdout 提取 JSON 对象 |

**关键超时常量**：

| 常量 | 值 | 用途 |
|------|-----|------|
| `STEP2_EXEC_TIMEOUT_SECONDS` | 86400（24h） | 步骤2 runner Popen 等待上限（monitor.tick 之外的第二道防线） |
| `STEP2_MONITOR_POLL_INTERVAL` / `STEP2_MONITOR_TIMEOUT` | 600s / 3000s | 产出感知监控轮询间隔 / 连续无变动超时（50min） |
| `STEP2_STDOUT_FALLBACK_TIMEOUT` | 9000s | 监控脚本不可用时的 stdout 静默兜底 |
| `STEP3_TIMEOUT_SECONDS` | 18000（5h） | 步骤3 采集 |
| `STEP3_5_TIMEOUT_SECONDS` | 14400（4h） | 步骤3.5 code-rating |
| `AGENT_CALL_TIMEOUT_SECONDS` | 86400×2（48h） | LLM agent 调用默认超时 |
| `AGENT_BASH_TIMEOUT_MS` | 43200000 | 被测 Agent CLI / LLM 子代理内部 Bash 超时（环境变量注入） |

### 3.8 会话级阶段与交付物验证（阶段E）

按 `profile.session_stages` 声明顺序遍历（默认四段，与原 run_driver 硬编码逐项等价）：

| 阶段 | 实现函数 | 说明 |
|------|---------|------|
| session_aggregate | `session_aggregate` | 阶段3.5：会话级聚合评估，仅 `plan.unified_evaluation=true` 时执行；收集各 subset 的 step4 结果（score/status/evaluation_file/dimension_scores）构造 prompt 调 evaluation-agent（aggregation_mode=true）；超时不阻断汇总 |
| results_summary | `update_plan_results_summary` | 阶段4.1a：确定性汇总；`aggregate_warnings` 累积语义（list 累积，旧字符串形态自动升级，resume 重跑不丢历史 warning） |
| aggregate_script | `run_aggregate_script`（result_key=aggregate_ok） | 阶段4.1b：`aggregate_evaluator_results.py` 汇总；解析 stdout JSON 的 `subset_count` 与 plan subset_details 数比对，不一致 → warning 写入 `aggregate_warnings`（不阻断，"缺失即标注"语义） |
| session_report | `session_report`（result_key=report_ok） | 阶段4.2：报告生成；失败（超时/exit 异常/交付物验证不过）→ **整体重试 1 次**（`_session_report_once`），仍失败返回 False 靠 `--resume` 断点重续兜底（不做 failed_reports 定向重调） |

- **每阶段执行前重读 plan**（聚合后/报告前各重读一次最新状态）。
- **阶段失败不中断后续阶段**（aggregate 异常仍继续报告生成，最终经退出码反映）。
- 报告生成后执行 `verify_final_deliverables`：`reports/index.html` 封面页 + 三份 per-subset
  子报告（single/product/process）为必查交付物，封面页失败同样触发阶段4.2 整体重试。

### 3.9 断点重续机制的引擎侧细节（补充第 10 章·断点续执行机制）

- **resume 语义**：全新执行与重续走同一路径（`run_driver` 的 resume 参数仅为 CLI 兼容保留，
  函数体内不读取）——各步骤 run() 内部的 completed 守卫 + resume_ready 跳过条件天然实现断点。
- **driver 主循环消费顺序 `resume_ready → should_run → run`**：resume_ready=True 的已终态步骤
  不得被门控重判覆盖为 skipped（如 task.json 事后被删时不得把已 completed 的 3.6 覆写为
  skipped）。
- **check action 不得丢弃（B2）**：全部步骤可跳过但 subset 状态非 completed（状态悬空，典型是
  step5 写入与 subset status 更新之间崩溃）→ 必须并入 pending 重入复核，各步骤有 completed
  守卫，实际落到 step5_verify 复核写回最终状态——静默丢弃会导致 subset 永久悬空且计数不感知
  （exit_code=0 但状态既非 completed 亦非 failed）。
- **复用 subset**：`reused=true` 直接跳过全部步骤置 completed（对应 5.5 节基线复用机制）。

### 3.10 关键陷阱速查表

| # | 约束 | 后果（违反时） |

| 11 | 步骤2 runner 必须指向 `.cac/skills/test-excel-runner/scripts/run_excel_tests.py`（不是 `.opencode` 下同名脚本） | runner 瞬间退出但 exit_code=0，被测 agent 从未执行 |

| 13 | plan 顶层 `pipeline` 字段（初始化脚本写入）优先于 CLI `--profile` | 参数优先级倒置 |

### 5.2 子用例集拆分

**并行策略**：

| 策略 | 条件 | 说明 |
|------|------|------|
| 全部并行 | 每个 (tech_stack, work_dir) 组只有1个 subset | 各子用例集资源独立 |
| 串行 | 同一 (tech_stack, work_dir) 有多个 subset | 共享资源，保证环境隔离 |
| 混合 | 部分组共享、部分独立 | 共享组串行，独立组并行 |

### 5.3 参考答案与规则集组织

目录结构：

│   └── ...

- **文件型答案**：目录下的参考代码/文档文件
- **MR列表型答案**：CodeHub MR URL 列表（格式 `MR列表{https://...}` 或 `MR:https://...`）

## 6. 评测全流程详解

### 6.0 总体流程

```
用户调用 / backend 下发
  │
  ├─→ 【前置阶段】规则集生成（可选，rubric-extractor）
  │     分析实例文件包 → 生成 contract.md + rubric.md
  │
  ├─→ 【阶段A】会话初始化 + 上下文校验（run_session_bootstrap.py）
  │     初始化（prepare_eval_session：验证用例集 → 拆分 → 生成执行计划，幂等）
  │     → 拉起 driver → driver 校验 session_id / plan 契约 → evaluate_checkpoint.py 断点检测
  │
  └─→ 【阶段B】执行执行计划（支持断点续执行）
        │
        ├─→ 阶段2：断点检测（evaluate_checkpoint.py）
        │
        ├─→ 阶段3：逐个执行子用例集（步骤1→2→3→3.5→3.6→4→5）
        │     │
        │     ├─ 步骤1: 准备目标执行上下文（用例来源二选一校验）
        │     ├─ 步骤2: Bash后台执行测试 + 产出感知等待
        │     ├─ 步骤3: 采集执行过程（collect_subset.py，内含 improving 链路B）
        │     ├─ 步骤3.5: 代码质量评分（prepare_code_rating.py，条件必做）
        │     ├─ 步骤3.6: 构建与测试执行（条件必做）
        │     ├─ 步骤4: 评估执行结果（→ evaluation-agent → evaluation-scenario）
        │     └─ 步骤5: 验证完整性（检查点）
        │
        ├─→ 阶段3.5: 会话级聚合评估（unified_fusion/model_upgrade场景）
        │
        └─→ 阶段4: 结果汇总 + HTML报告生成
              ├─ 4.1: 确定性统计 + aggregate_evaluator_results.py 汇总
              └─ 4.2: 调用report-generator生成HTML报告
                    ├─ single 报告 × N（每个 subset 一份，含主报告+产物子报告+过程子报告）
                    ├─ comparison 报告 × 1（对比场景，含主报告+产物子报告+过程子报告）
                    └─ 封面页 index.html（所有场景必交，生成失败触发 4.2 整体重试）
```

### 6.1 步骤1：准备目标执行上下文

- 用例来源**二选一**校验：Excel 副本（`excel_copy_path`）或会话隔离 JSON（`usecase_json_path`），二者不得同时存在也不得同时缺失
- 验证 `output_dir`、`case_count` 等路径字段有效
- 失败 → subset 置 failed 且**中断**（后续步骤依赖其产物路径校验）
- 更新执行计划状态

### 6.2 步骤2：执行测试并捕获结果

**启动测试任务**（runner 以 `cwd=work_dir` 在被测工作区执行）：
```bash
# Excel 副本链路（原链路）
python ".cac/skills/test-excel-runner/scripts/run_excel_tests.py" "{excel_copy_path}" "{session_id}"

# plan.json 链路（cac 模式，按 subset_id 过滤）
python ".cac/skills/test-excel-runner/scripts/run_excel_tests.py" \
  --plan-json {plan_path} --subset-id {subset_id} --output-dir {output_dir} "{session_id}"
```
- Popen 等待超时 ≥ 24 小时（86400s）
- exec_dir 必须取自执行计划的 `work_dir`（拷贝后的工作区路径）

**产出感知等待**（driver 并行拉起监控子进程）：
```bash
python ".cac/scripts/output_aware_wait.py" \
  --exec-dir {work_dir} \
  --log-dir {output_dir}/评测输出 \
  --heartbeat-file {output_dir}/monitor_heartbeat.json \
  --poll-interval 600 \
  --timeout 3000
```

**termination_reason 判定**（三值契约）：

| 情况 | termination_reason | 触发条件 |
|------|-------------------|---------|
| 正常返回 | `normal_return` | runner 自行退出且 exit_code=0 |
| 异常终止 | `abnormal_kill` | runner 自行退出但 exit_code≠0（进程异常终止） |
| 超时终止 | `timeout_fallback` | 产出感知监控超时 / stdout 静默兜底超时 / 全局超时，driver 主动整树杀 |

**关键约束**：runner stdout 读取放独立线程、主循环短间隔轮询（单点收敛于 `_stream_subprocess`，多通道终止判定经 `on_tick` 钩子注入，见 §3.7）；禁止复制该消费循环。

### 6.3 步骤3：采集执行过程

```bash
python .cac/scripts/collect_subset.py \
  --plan-file {plan_path} \
  --subset-id {subset_id} \
  --artifacts-file {timestamp_dir}/subset_artifacts.json
```

**双链路并行采集**：
- **链路A**：collector 直接产出 HTML 分析报告 + summary JSON（核心结构化数据源）
- **链路B**（improving-evaluation）：深度分析 HTML 报告（耗时分析/瓶颈/知识消费/执行证据）

**产出文件**：
| 文件 | 路径 | 说明 |
|------|------|------|
| 分析报告(链路A) | `reports/{subset_id}/collector/{case_id}_analysis_report.html` | 概览/产出物/API详情/token统计/工具统计/时间线 |
| Summary JSON | `reports/{subset_id}/collector/{case_id}_analysis_report_summary.json` | 结构化数据 |
| Diff日志 | `reports/{subset_id}/collector/{case_id}_diff_log.json` | 代码变更详情 |
| 深度分析报告(链路B) | `reports/{subset_id}/improving/{case_id}/html-report/index.html` | 耗时/瓶颈/知识消费/执行证据 |

> 链路B（improving-evaluation）耗时 1-3 小时/轮，多用例串行总耗时可能超过 5 小时。

### 6.3.5 步骤3.5：代码质量评分（条件必做）

**触发条件**：参考答案目录包含 MR URL

```bash
python .cac/skills/code-rating/scripts/prepare_code_rating.py \
  --plan-file {plan_path} \
  --subset-id {subset_id} \
  --artifacts-file {timestamp_dir}/subset_artifacts.json \
  --output-dir {output_dir}/code_rating \
  --report-publish-dir {timestamp_dir}/reports/{subset_id}/code_rating \
  --concurrency 3 -v
```

**执行流程**：
1. 解析变更清单 JSON（`agent_code_changes.py` 产出）
2. 从 eval-base tag 导出 baseline 文件
3. 生成 patch 文件（支持工作树快照，排除预存未提交改动）
4. 生成 rating_config.json
5. 调用内嵌 auto_code_rating CLI（LLM 逐文件评分）
6. 发布报告

**CodeHub 鉴权（凭证优先级）**：PAT 直连优先——`--token` > `.cac/config.json` 的 `codehub_token` > 环境变量 `CODEHUB_TOKEN`；提供 PAT 时拉取标准答案 MR 走 PRIVATE-TOKEN 直连通道（不需要 account/password）。未提供 PAT 时回退 account/password 网关通道（优先级同上：CLI > `.cac/config.json` > env `CODEHUB_ACCOUNT`/`CODEHUB_PASSWORD`）。

**产出**：`original_data.json`（完整评分数据）、`index.html`（概览报告）、`detail/*.html`（明细页）

**硬性执行规则**：
- 有 MR URL 时禁止以"节省token"/"耗时过长"为由跳过
- skip_reason 属于三种合法取值之一（与 driver 实际写入一致）：无 MR URL（门控跳过，正常语义）/ 评分脚本超时且无部分产出 / 评分脚本执行失败（exit_code≠0；超时但有部分产出时记 completed + `partial=true`，保留评分数据不跳过）
- 跳过有 MR URL 的 code-rating 会导致 code_quality 维度降级：`model_quality` 无 code_similarity 数据，退化为纯 LLM 评分（`model_quality = llm_code_analysis`，缺失"有 code_similarity 时 `model_quality = code_similarity × 0.5 + llm_code_analysis × 0.5`"的合成），再与 B2/B3 动态加权

### 6.3.6 步骤3.6：构建与测试执行（条件必做）

**触发条件**：`task.json`（路径 `评测用例&答案/tasks/{用例名}/{子用例名}/task.json`）存在且 `validation.compileCommands`/`validation.focusedTests` 非空

从 `task.json` 读取构建和测试命令，在 `work_dir` 下执行，产出：
- `build_result.json`（status: passed/failed, total_commands, passed_commands, failed_commands, commands[]）
- `test_result.json`（status, total_tests, passed_tests, failed_tests, commands[]）

**关键约束**：构建/测试失败不中断后续步骤，失败结果传递给 evaluation-agent 在 `build_pass_rate`/`test_pass_rate` 子维度反映为低分；跳过时对应子维度 score=null，动态加权时忽略。

### 6.4 步骤4：评估执行结果

通过 `codeagent --agent evaluation-agent` CLI 一次性调用（并行波内随 subset 线程并发），evaluation-agent 内部：
1. 调用 `evaluation_prepare.py` 脚本化提取上下文（含 rubric_file、contract_file、build_result_file、test_result_file 约定路径推导 + 第0步数据完整性检查，缺失记 data_gaps）
2. 调用 evaluation-scenario skill（按脚本输出 args 透传）
3. evaluation-scenario 根据场景选择调用 integrated-evaluation skill
4. 调用 `evaluation_finalize.py` 脚本化组装返回值（算术矫正 + 字段回填 + 产物磁盘验证）

### 6.5 步骤5：验证完整性

| 检查项 | 验证内容 |
|-------|---------|
| 步骤1-4完成 | steps_progress 中 step1~step4 均为 "completed"（条件步骤 3.5/3.6 允许 completed\|skipped） |
| 步骤2产出 | execution_result 已持久化且完整 |
| 步骤3产出 | collector_output 中文件路径在磁盘上存在 |
| 步骤3.5产出 | status 为 "completed" 或 "skipped"，skip_reason 已记录 |
| 步骤3.6产出 | status 为 "completed" 或 "skipped"，skip_reason 已记录 |
| 步骤4产出 | evaluation_output 已持久化，产物路径磁盘存在 |

> 必过清单从 Profile 步骤聚合，**不含 step5_verify 自身**（自指防护，见 §3.5/§3.10）。通过 → subset 置 completed；不通过 → step5 记 failed + subset 置 checkpoint_failed。

### 6.6 阶段3.5：会话级聚合评估

**触发条件**：`unified_evaluation=true`（统一融合 / 模型升级场景）

```
codeagent --agent evaluation-agent --print -- \
  "执行会话级聚合评估（unified_fusion）：
    plan_file={plan_path}，
    session_id={session_id}，
    timestamp_dir={timestamp_dir}，
    unified_evaluation=true，aggregation_mode=true，
    subset_results_summary={subset_results_summary}。
    你必须严格按照子代理系统提示词的步骤执行，不要遗漏任何步骤。"
```

其中 `subset_results_summary` 从各 subset 的 step4 `evaluation_output` 确定性收集（subset_id/score/status/evaluation_file/report_file/html_report_path/dimension_scores），reused subset 不纳入。

**关键约束**：不重复执行逐用例评估，只消费阶段一已产出的结果文件做跨 subset 聚合。

## 7. 打分标准体系

### 7.1 评分体系总览（产物评判 / 过程评判）

评分标准采用**两级分类**体系：

```
最终评分（产物类场景） = feature_completeness × 0.50 + code_quality × 0.40 + performance_trace × 0.10
通过条件 = 最终评分 >= 0.70 AND feature_completeness >= 0.60

├─ 产物评判
│   ├─ A. 功能实现完整性 (feature_completeness) — 权重 0.50
│   │     数据源：rubric.md（核心）+ contract.md（辅助）
│   │
│   └─ B. 代码质量 (code_quality) — 权重 0.40（三子维度动态加权）
│         ├─ B1. 模型质量分析 (model_quality) — 默认权重 0.5
│         │     ├─ B1a. 代码相似度评估 (code_similarity) — code-rating 引擎
│         │     └─ B1b. LLM 代码质量分析 (llm_code_analysis) — 10 检查项
│         ├─ B2. 构建通过率评估 (build_pass_rate) — 默认权重 0.3
│         └─ B3. 测试通过率评估 (test_pass_rate) — 默认权重 0.2
│
└─ 过程评判
    └─ C. 性能轨迹分析 (performance_trace) — 权重 0.10（产物类场景降权；性能对比场景为主维度）
          ├─ C1. 执行轨迹详情分析 (execution_trace) — 整合 self-improving
          └─ C2. 模型响应质量 (response_quality)
```

### 7.2 维度 A：功能实现完整性 (feature_completeness) — 权重 0.50

**数据源**：`ground-truth/rubric.md`（核心）+ `contract.md`（辅助）

**打分方法**：从 `rubric.md` 解析功能项清单（rubric_groups/items），对实际产出逐项判定实现情况。

**rubric.md 格式**：
```markdown
# 盲评产品评分标准（100 分）

## 1. 维度名称 - 20
- 原子评分项: 8
- 原子评分项: 7
- 原子评分项: 5

## 验证标签
Verified / Static / Unverified / Contradicted
```

**逐项判定**：
| 判定 | 得分系数 | 说明 |
|------|---------|------|
| `fully_implemented` | 1.0 | 明确满足，有代码证据 |
| `partially_implemented` | 0.5 | 基本满足但有小遗漏 |
| `not_implemented` | 0.0 | 未实现或逻辑错误 |
| `unknown` | 不计入 | 证据不足，不强迫猜测 |

**计算公式**：`feature_completeness = Σ(item_score × item_points) / Σ(已判定项 item_points)`

**验证标签**：每项同时记录 Validation label（`Verified` / `Static` / `Unverified` / `Contradicted`），与分数独立记录，不因只能静态确认就自动判失败。

**降级**：rubric.md 缺失时，回退到从 expected_output_file 提取关键功能要素清单做逐项检查，confidence × 0.7。

### 7.3 维度 B：代码质量 (code_quality) — 权重 0.40

**动态加权机制**：三个子维度动态加权，缺失项忽略（score=null），剩余项按原比例加权求总分：

```python
available = {k: v for k, v in sub_dims.items() if v["score"] is not None}
total_weight = sum(v["weight"] for v in available.values())
code_quality = sum(v["score"] * v["weight"] for v in available.values()) / total_weight
```

| 子维度 | 默认权重 | 数据来源 |
|--------|---------|---------|
| B1. 模型质量分析 (model_quality) | 0.5 | code-rating + LLM 10检查项 |
| B2. 构建通过率评估 (build_pass_rate) | 0.3 | task.json compileCommands → build_result.json |
| B3. 测试通过率评估 (test_pass_rate) | 0.2 | task.json focusedTests → test_result.json |

#### B1. 模型质量分析 (model_quality)

**统一打分，提供整合分析**。下设两个子项：

```
有 code_similarity 时：model_quality = code_similarity × 0.5 + llm_code_analysis × 0.5
无 code_similarity 时：model_quality = llm_code_analysis（纯 LLM 评分）
```

**B1a. 代码相似度评估 (code_similarity)**：来自 code-rating 引擎 `summary.matched_weighted_total_score`（0-100 → 归一化 0-1.0）

**B1b. LLM 代码质量分析 (llm_code_analysis)** — 10 个检查项，布尔判定 + 严重度标注（high/medium/low），扣分制：

| # | 检查项 | 权重 |
|---|--------|------|
| 1 | 是否改变公共接口 | 0.15 |
| 2 | 是否修改过多无关文件 | 0.10 |
| 3 | 是否删除已有逻辑 | 0.10 |
| 4 | 是否放宽关键校验 | 0.10 |
| 5 | 是否吞掉异常 | 0.10 |
| 6 | 是否改变默认行为 | 0.10 |
| 7 | 是否增加未经处理的新分支 | 0.05 |
| 8 | 是否修改测试或绕过校验 | 0.10 |
| 9 | 是否有大规模无关重构 | 0.10 |
| 10 | 是否引入明显的资源/安全/并发风险 | 0.10 |

扣分公式：
```
severity_factor = {"high": 1.0, "medium": 0.6, "low": 0.3}
deduction = Σ(weight × severity_factor[severity] for violated items)
llm_code_analysis = max(0, 1.0 - deduction)
```

#### B2. 构建通过率评估 (build_pass_rate)

来自步骤3.6 `build_result.json`：passed=1.0 / failed=0.0 / skipped=null（动态加权忽略）

#### B3. 测试通过率评估 (test_pass_rate)

来自步骤3.6 `test_result.json`：`score = passed_tests / total_tests`，skipped=null（动态加权忽略）

### 7.4 维度 C：性能轨迹分析 (performance_trace) — 权重 0.10

```
performance_trace = execution_trace × 0.6 + response_quality × 0.4
```

> 产物类场景权重 0.10；性能对比场景提升为主维度。

#### C1. 执行轨迹详情分析 (execution_trace) — 整合 self-improving，扣分制，基准1.0

**数据源**：improving-evaluation 的 `time_analysis` + `process_anomalies.json` + collector 的 tool_stats

| 指标 | 来源 | 扣分逻辑 | 上限 |
|------|------|---------|------|
| 低效行为次数 | process_anomalies | 每次 -0.05 | -0.25 |
| 瓶颈严重度 | bottleneck_summary | 严重-0.15 / 中等-0.08 | -0.15 |
| 知识消费未满足率 | knowledge_unmet / knowledge_reads | 率>0.3 时 -0.10 | -0.10 |
| 幻觉检测 | halluc_status | 确认-0.20 / 疑似-0.10 | -0.20 |
| 工具调用错误率 | tool_stats error_rate | 率>0.2 时 -0.10 | -0.10 |
| 重复搜索/盲目试错 | process_anomalies rules | 每类 -0.05 | -0.15 |

#### C2. 模型响应质量 (response_quality) — 扣分制，基准1.0

**数据源**：collector `summary_json` 中 api_calls 数组

| 检查项 | 扣分逻辑 | 上限 |
|--------|---------|------|
| 401/403 认证错误 | 每次 -0.15 | -0.30 |
| 500 服务器错误 | 每次 -0.10 | -0.30 |
| 429 限流错误 | 每次 -0.05 | -0.15 |
| 异常响应 | 每次 -0.10 | -0.20 |
| 响应过慢（P95 > 60s） | -0.15 | -0.15 |
| 重试次数过多（>0.3） | -0.10 | -0.10 |

### 7.5 评分量表

| 等级 | 分值 | 判定标准 |
|------|------|----------|
| Excellent | 1.0 | 完全满足，无瑕疵 |
| Good | 0.8 | 基本满足，有轻微不足 |
| Acceptable | 0.6 | 关键点满足，有明显缺陷 |
| Poor | 0.3 | 重大缺失或错误 |
| Failed | 0.0 | 核心要求未达到 |

### 7.6 偏差缓解机制

| 偏差类型 | 必须执行 | 执行动作 |
|---------|---------|----------|
| Position Bias | ✅ 必须 | Position Swap（两轮 + 映射 + 一致性检查） |
| Length Bias | ✅ 必须 | 显式反偏差指令 + 检测长度-评分正相关 |
| Self-Enhancement | ⚠️ 建议 | 建议使用交叉模型；无法实现时标注声明 |
| 盲评 | ⚠️ 建议 | 移除输出中的模型标识信息 |

### 7.7 Confidence Calibration

| 信号 | 调整 |
|------|------|
| Position Swap 两轮不一致 | confidence × 0.6 |
| 证据不足 3 条 | confidence × (0.7 + 0.3 × evidence_count/3) |
| code_quality 有子维度缺失 | confidence × 0.85 |
| performance_trace 有数据源缺失 | confidence × 0.85 |
| rubric.md 缺失回退到旧流程 | confidence × 0.7 |
| 上限 | 永远不超过 0.99 |

## 8. 支持的评测场景

### 8.1 场景速查表

| 场景 | mode 参数 | 触发条件 | 评估范围 | 核心产出 |
|------|----------|---------|---------|---------|
| **统一融合评估-聚合** | `unified_fusion` | `unified_evaluation=true` 且 `aggregation_mode=true` 且非模型升级 | 全会话所有 subset | 技术底座对比 + 融合报告 |
| **模型升级场景评估-聚合** | `model_upgrade` | `unified_evaluation=true` 且 `aggregation_mode=true` 且检测为模型升级 | 全会话所有 subset | 能力对比矩阵 + 过程维度指标 + 升级建议 |
| **答案对比**（阶段一） | `answer_comparison` | 提供 `reference_answer_directory` 且未开启统一评估；或 `unified_evaluation=true` 但 `aggregation_mode` 未传 | 单个用例 | `{case_id}_evaluation.json` + HTML 报告 |
| **性能对比**（阶段一） | `performance_comparison` | 提供 `comparison_target` 且未开启统一评估聚合 | 同一任务两技术底座性能 | 对比报告 |

### 8.2 场景选择决策流程

```
收到评估任务
  │
  ├─ aggregation_mode: true？
  │   ├─ 是 → 会话级聚合模式（阶段二）
  │   │   ├─ unified_evaluation: true？
  │   │   │   ├─ 是 → 执行模型升级场景判断逻辑
  │   │   │   │   ├─ 满足模型升级条件 → model_upgrade（聚合）
  │   │   │   │   └─ 不满足 → unified_fusion（聚合）
  │   │   │   └─ 否 → 错误：aggregation_mode=true 必须配合 unified_evaluation=true
  │   │   └─ 消费 subset_results_summary 中的阶段一结果，跳过逐用例评估
  │   └─ 否 → 单子用例集评估模式（阶段一）
  │       ├─ unified_evaluation: true？
  │       │   ├─ 是 → 阶段一仍走 answer_comparison（unified_evaluation 仅作标记）
  │       │   └─ 否 → 有 reference_answer_directory → answer_comparison；有 comparison_target → performance_comparison
```

### 8.3 模型升级场景判断逻辑

当 `unified_evaluation=true` 时：

1. 提取所有 subset 的 tech_stack，解析为 (agent框架, 模型名, 其他组件) 三元组
2. 判断条件（全部满足则判定为模型升级场景）：
   - 所有 subset 的 agent框架 相同
   - 所有 subset 的 其他组件 相同
   - 各 subset 的 模型名 不同
   - subset 数量 >= 2
3. 特殊情况：模型名格式不同但属同一系列归一化后比较；tech_stack 无法拆分为三元组 → 走默认统一融合评估；混合场景 → 走默认统一融合评估

### 8.4 答案对比模式详细流程

1. **数据完整性检查**（第0步，不可跳过）— 含 rubric/contract/task.json/build_result/test_result 检查
2. **输入准备**：读取 collector 汇总 JSON + HTML 分析报告 + Excel 参考答案
3. **期望输出解析**：文件型/MR列表型/纯文本 → 写入 `{case_id}_expected.json`
4. **实际输出解析**：从 collector 获取执行状态、生成文件、代码变更 → 写入 `{case_id}_actual.json`
5. **期望 vs 实际对比**：逐文件对比 → 写入 `{case_id}_comparison.json`
6. **评估执行**：调用 integrated-evaluation skill → Direct Scoring + Position Swap
7. **HTML报告生成**：collect_report_data.py → LLM填JSON → render_report.py
8. **结果输出**：`{case_id}_evaluation.json` + `{case_id}_evaluation.md` + `{case_id}_integrated_evaluation_result.json` + `{case_id}_evaluation_report.html`
9. **异常根因分析**（score < 0.70 或 status=fail 时）

### 8.5 性能对比模式详细流程

1. 读取评测A/B的 collector 输出文件
2. 分别计算 A/B 的 execution_trace 和 response_quality 得分
3. Pairwise Comparison 对比两组的 performance_trace 指标
4. Position Swap：交换A/B位置后再次评估，取两次评分的平均值
5. 耗时对比分析（总耗时、API响应时间、Token生成速度、Tool调用效率）
6. 输出对比评估结果

### 8.6 统一融合评估模式详细流程

**阶段一**：每个 subset 按 answer_comparison 模式执行逐用例评估

**阶段二**（`aggregation_mode=true`）：
1. 消费阶段一结果（`subset_results_summary`）
2. 按技术底座分组汇总（总用例数、通过率、平均评分、总耗时、总Token）
3. 耗时对比分析
4. 生成融合报告

### 8.7 模型升级场景评估模式详细流程

**阶段一**：每个 subset 按 answer_comparison 模式执行逐用例评估

**阶段二**（`aggregation_mode=true`）：
1. 模型分组与标注（旧模型 vs 新模型）
2. 消费阶段一结果
3. **专项指标采集**：
   - 数量类：Token消耗量、总执行时长、首Token延迟、生成速率、重试次数、API调用效率、Tool调用数与分布
   - 质量类：功能实现完整性、代码质量、性能轨迹（对接三维度评测体系）
4. 差异计算：`差异百分比 = (新模型值 - 旧模型值) / 旧模型值 × 100%`
5. 生成模型升级报告
6. 升级建议：推荐升级 / 需谨慎 / 不建议升级

## 10. 断点续执行机制

### 10.1 续执行场景

| 场景 | 状态 | 处理 |
|------|------|------|
| 全新执行 | 计划文件已由 run_session_bootstrap.py 预生成 | 全部 subset 从头执行 |
| 子用例集级续执行 | 部分subset为pending | 从第一个非completed的subset继续 |
| 步骤级续执行 | subset为running，部分步骤completed | 从第一个非completed步骤继续 |
| 失败重试 | subset为failed/checkpoint_failed | 从失败步骤继续 |
| 全部完成 | 所有subset为completed | 直接汇总 |
| 指定session续执行 | 用户提供session_id | 读取对应计划文件续执行 |

### 10.2 断点检测

```bash
# 自动扫描所有未完成计划（最新优先）
python .cac/scripts/initiator/evaluate_checkpoint.py

# 指定 session_id
python .cac/scripts/initiator/evaluate_checkpoint.py --session-id {session_id}
```

### 10.3 状态定义

**子用例集状态**：

| 状态 | 说明 | 可否续执行 |
|------|------|-----------|
| `pending` | 未开始 | ✅ |
| `running` | 执行中（中断后） | ✅ 从未完成步骤继续 |
| `completed` | 全部步骤完成 | ❌ 跳过 |
| `failed` | 执行失败 | ✅ 从失败步骤继续 |
| `checkpoint_failed` | 检查点失败 | ✅ 从失败步骤继续 |

**步骤状态**：`pending` → `running` → `completed` / `skipped` / `failed`

## 11. 报告生成体系

### 11.1 报告类型

| 报告类型 | 模板文件 | 适用场景 | 说明 |
|----------|---------|---------|------|
| 封面页/报告总览 | `evaluation_index_report.html` | 所有场景 | index.html，全部报告的跳转入口（独立链路，不走 collect → schema → render） |
| 单子用例主报告 | `evaluation_single_report.html` | 所有场景 | 一句话结论 + 总览指标 + 维度评分 + 能力亮点/改进方向 |
| 单子用例-产物子报告 | `evaluation_single_product_report.html` | 所有场景 | 核心指标 + **维度矩阵（含权重列+最终得分行）** + 逐用例评分链接 + code_rating 链接 |
| 单子用例-过程子报告 | `evaluation_single_process_report.html` | 所有场景 | 轨迹分析（耗时/知识/幻觉/异常/Token） + 性能指标 + 行动建议 |
| 对比主报告 | `evaluation_comparison_report.html` | 对比场景 | 一句话结论 + 总览对比矩阵 + 升级评估（能力提升/劣化） + 综合建议 |
| 对比-产物子报告 | `evaluation_comparison_product_report.html` | 对比场景 | 核心指标对比 + **维度矩阵对比（含权重列+最终得分行）** + 逐用例评分对比 |
| 对比-过程子报告 | `evaluation_comparison_process_report.html` | 对比场景 | 轨迹分析对比 + 性能指标对比 |
| 单子用例详细打分 | `subcase_evaluation_report.html` | 逐用例 | 维度评分明细、rubric 功能项明细、证据、改进建议 |

### 11.2 对比报告触发条件

**触发条件**：当会话中存在 **≥2 个不同 `tech_stack` 的 subset** 时必须生成对比报告。

**对比场景类型**：

| 场景类型 | 示例 | left/right 标签 |
|---------|------|----------------|
| 模型升级 | `cc+glm5.1` vs `cc+glm5.2`（同框架不同模型） | left=旧模型，right=新模型，label 用模型名 |
| 技术底座/框架优化 | `cc+datacom-sdd-nce` vs `cc+datacom-sdd-dt`（同模型不同组件） | left=优化前，right=优化后，label 用 tech_stack 简称 |
| 跨技术底座对比 | `cc+xxx` vs `oc+yyy`（不同框架） | left/right 按 tech_stack 字典序，label 用 tech_stack 简称 |

**多于 2 个不同 tech_stack 的处理**：当前 comparison 报告支持两两对比。若会话有 >2 个不同 tech_stack，driver 按 `build_report_types()` 确定性选取——tech_stack 字典序排序后，**left = 第一个 stack 的第一个 subset，right = 最后一个 stack 的最后一个 subset**，label 取 tech_stack；其余 subset 的详情在各自的 single 报告中展示。复用 subset（reused=true）计入对比判定，但不进 single 报告列表。

### 11.3 报告生成流程（report-generator）

```
步骤1: 解析任务参数
  │
步骤2: 生成 Single 报告（每个 subset 一份，共 3 个 HTML）
  ├─ 2.1: collect_report_data.py --mode single → report_data.json
  ├─ 2.2: LLM 填充 [LLM] 字段（executive_summary、strength_list、weakness_list 等）
  └─ 2.3: render_report.py × 3（single + single_product + single_process）
  │
步骤3: 生成 Comparison 报告（对比场景，共 3 个 HTML）
  ├─ 3.1: collect_report_data.py --mode comparison → report_data.json
  ├─ 3.2: LLM 填充 [LLM] 字段（upgrade_recommendation、improvement_list 等）
  └─ 3.3: render_report.py × 3（comparison + comparison_product + comparison_process）
  │
步骤4: 生成封面页 index.html（generate_report_index.py，所有场景；失败需排查重试，
        封面页缺失会被交付物验证拦截并触发阶段4.2 整体重试）
  │
步骤5: 验证所有 HTML 文件存在（含 index.html）
```

### 11.4 能力维度矩阵

**`evaluation_single_product_report.html` 和 `evaluation_comparison_product_report.html`** 的能力维度矩阵新增：

1. **"权重"列**：表头新增 `权重` 列，循环块 item 模板新增 `{{DIM_WEIGHT}}` 单元格（如 `50%` / `40%` / `10%`）
2. **"最终得分"行**：tbody 末尾新增静态"最终得分"行，引用 `{{FINAL_SCORE}}` / `{{FINAL_SCORE_CLASS}}`（single）或 `{{FINAL_SCORE_LEFT}}` / `{{FINAL_SCORE_RIGHT}}`（comparison）
3. **悬浮标识**（`score-tip`）：评分项添加悬浮提示，说明权重分配和最终得分计算公式："最终得分 = Σ（各维度得分 × 对应权重），权重：功能实现完整性 50% · 代码质量 40% · 性能轨迹分析 10%"

### 11.5 数据采集链路

```
原始日志
  → agent_log_analyzer.py          (采集日志，生成 summary_json)
  → analyze_token_log_cac.py       (生成 token_rate_report.md)
    → build_step1_report.py        (从 markdown 解析，生成 time_analysis JSON)
      → improving JSON
        (self-improving-report-input.md)
          → collect_report_data.py (提取 PQ 快照 → report_data.json)
            → render_report.py     (标量映射 + 循环展开)
              → HTML 模板
```

### 11.6 Schema 校验

报告数据通过 JSON Schema (`report_data.schema.json`) 校验，占位符映射通过 `_validate_schema.py` 管理。修改报告链路后必须运行 `python .cac/scripts/test/test_report_pipeline.py` 验证。

### 11.7 报告生成数据链路修改清单

新增/修改报告指标时，必须沿完整数据链路逐层修改：

| 层级 | 文件 | 改动要点 |
|------|------|----------|
| 1. 数据源 | improving-evaluation 脚本 | 在全局概览 markdown 表中新增指标行 |
| 2. 解析层 | `build_step1_report.py` | 在 time_analysis dict 中新增字段 |
| 3. 校验层 | `build_report.py` | 加入新字段校验 |
| 4. 收集层 | `.cac/scripts/collect_report_data.py` | 提取新字段到 PQ 快照 / capability_rows |
| 5. 渲染映射 | `.cac/scripts/render_report.py` | 新增占位符 → 值映射 |
| 6. 模板 | `.cac/templates/evaluation_*.html` | 添加 `{{占位符}}` |
| 7. Schema | `.cac/schemas/report_data.schema.json` | 新增字段定义 |
| 8. 占位符映射 | `.cac/schemas/_validate_schema.py` | 新增占位符 → schema 路径映射 |
| 9. 测试 | `.cac/scripts/test/test_report_pipeline.py` | KNOWN_LOOP_VARS 新增；mock 数据补充 |

**关键注意事项**：
- 单侧报告使用 `{{FIELD_NAME}}`，对比报告使用 `{{FIELD_NAME_LEFT}}` / `{{FIELD_NAME_RIGHT}}`
- Schema 的 `additionalProperties: false` 意味着未在 schema 声明的字段会导致校验失败
- 新增 single 对象级别的必填字段时，必须同步加入 schema `required` 列表
- `render_template` 函数签名：`render_template(data, template, mode)` — 第二参数是模板文件**内容字符串**，不是文件路径
- improving JSON 从 `self-improving-report-input.md` 中的 fenced JSON code block 读取
