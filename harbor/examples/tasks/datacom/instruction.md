# datacom：入口限流与背压

`/app` 是一个已经存在的 `datacom` 工程（数据通信组件，负责接收、校验、转发记录）。
它已经在生产里跑，因此**向下兼容是硬约束**。

## 背景

上游突发流量会把下游 sink 打挂。已有的重试机制只处理单条记录失败，
对"整体吞吐超过下游承载能力"没有任何保护。

## 需求

给 `datacom` 增加**入口限流与背压**能力，满足以下要求：

1. **可配置速率上限**：按每秒记录数（records/s）限制入口接收速率，
   配置来源与工程现有的配置方式保持一致。
2. **背压而非丢弃**：超限时优先对上游施加背压（暂停读取/返回可重试信号），
   只有在明确配置了"允许丢弃"时才丢弃，且丢弃必须计数并可观测。
3. **公平性**：多个上游连接共享同一速率预算，不得让单个连接饿死其他连接。
4. **平滑**：不得出现"攒够配额一次性放行"的突发（burst），
   放行节奏应当平滑（例如令牌桶 + 有界突发，或漏桶）。
5. **可观测**：暴露被限流次数、当前速率、丢弃计数，接入工程已有的指标机制。
6. **不破坏现有行为**：未配置限流时，行为与当前版本完全一致。

## 执行方式

使用你的 **`datacom-sdd` 技能套件**，按它的三个阶段顺序执行，不要跳步：

1. **规格阶段** —— 产出 `/app/spec.md`
2. **计划阶段** —— 产出 `/app/plan.md`
3. **实现阶段** —— 按计划改代码，并跑通构建与你自己的测试

阶段顺序和方法论以技能套件里的说明为准；本文件只负责给需求和产物位置。

## 必须留下的产物

| 路径 | 说明 |
| --- | --- |
| `/app/spec.md` | 规格说明：接口契约、行为规则、非功能要求、非目标 |
| `/app/plan.md` | 实现计划：需求追溯、设计、接口、工作拆解、验证策略 |
| `/app/**` | 实现代码。**必须在 `/app` 这个 git 仓库内改动**，评测端靠 diff 判断改动范围 |
| `/logs/artifacts/` | 任何你希望评测端额外看到的中间产物（可选） |

## 约束

- 不要删除或放宽现有的测试；不要为了让测试通过而改动测试断言。
- 不要改动与本次需求无关的文件。
- 限流配置的默认值必须是"关闭"，否则会破坏现有部署。
- 你可以在 `/app` 里自由运行构建与测试来验证自己的工作。
